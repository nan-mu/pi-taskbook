# pi-taskbook

从「修复空输入时的报表」到一个可以接手的提交，中间有几种不同的问题。空输入真的会失败吗？修复后用户应该看到什么？谁来选方案，又凭什么说这个版本已经修好？Pi Taskbook 把这些判断分给掌握相应信息的人，并要求每个阶段交出下一步可以核查的结果。

## 谁来消除哪种不确定性

| 待解决的问题 | 谁来判断 | 下一阶段能依赖什么 |
| --- | --- | --- |
| 用户要改变什么？有哪些必须保留的选择？ | 用户与任务书作者确定可观察的目标，确认技术栈、接口约束等影响全局的事实。 | 一份说明目标、已知条件和交付要求的任务书。 |
| 任务的前提成立吗？ | 主会话核查现有行为。修复任务先观察故障，新增任务先确认能力缺口，再将随任务而来的事实与项目事实核对。 | 有来源和适用范围的事实，以及需要用户裁决的冲突。 |
| 从目标到成品还有哪些设计选择？ | 组长根据事实核查起草一份方案。两位成员独立找漏项、验收反例和事实冲突。有具体问题时，由组长修订或说明依据。 | 两位成员确认、组长签署的同一版实施方案。 |
| 代码该怎么写？ | 实施者按已签方案决定函数命名、局部结构等实现细节。发现方案缺口时，把具体观察交还设计者。 | 一个可复查的候选提交，以及在该版本上取得的验证结果。 |
| 这个版本可以交付吗？ | 两位审核者分别检验同一提交和证据，组长签署结论。需要返工时，新提交重新接受审核。 | 交付提交、验证结果、已知限制，以及经审核登记的事实变更。 |

## 为什么要有事实系统

任务书中的「保留原有报表表头」可以是一条经用户确认的约束。「空输入触发了异常」则需要给出能复核的输入和版本。将它们分别记录，设计者就能查清自己必须遵守什么，审核者也能回到相同条件检查结果。

用 `taskbook_query_facts` 按事实 ID、标签或文字检索项目事实。已有事实继续用原文件路径和行 ID 引用。任务携带的变更先保存在本轮任务视图里，经审核后登记。插件给每个子代理当前工作所需的材料，设计者和审核者可以按需查证据。

## 使用

在运行 Pi 的环境安装插件。

```sh
pi install https://github.com/nan-mu/pi-taskbook
```

| 命令 | 用户会得到什么 |
| --- | --- |
| `/taskbook-help [问题]` | 了解 Taskbook 的入口、分工和交付方式。用 `/taskbook-help status` 查看当前会话的任务阶段、待决事项或 PR。 |
| `/taskbook-setup` | 查看当前项目的就绪情况。可继续指定模型配置，或要求处理旧资料。 |
| `/taskbook <任务书路径或 Markdown 正文>` | 在当前会话启动任务。T3 会话尚未绑定工作树时，T3 按任务书指定的基线和 `Work branch` 创建工作树，并把当前会话迁过去继续事实核查。 |
| `/taskbook-new <任务书路径或 Markdown 正文>` | 请求 T3 创建工作树，并在新会话启动任务。 |

粘贴正文时，在命令后留一个空格，再粘贴多行 Markdown。正文中的事实写在 `## Facts` 下。引用相对路径的附件时，提交任务书文件的路径。需要裁决时在当前会话直接回复。任务中断或 Pi 重启后，再次执行 `/taskbook` 会开始一轮新任务。

在 Design 和 Implement 中，agent 提交工作结果时选择下一状态。插件加载该状态的提示词，并等待派发的工作全部返回。需要追查当前行为或历史决策时，可以选择 `how` 或 `why`。Design 的签署归档会记录成员发现的问题和组长的处理结果。

审核签署后，插件用 Git 推送任务分支，再用当前 Pi 会话的 Magpie GitHub 工具创建 PR，并等待回执。已有对应 PR 时更新该 PR。任务书无需声明发布，是否合并由你决定。

任务书的输入字段和引用规则见[任务书格式](.fact/taskbook-format/)；各阶段承担的判断见[工作流](.fact/workflow/)。
