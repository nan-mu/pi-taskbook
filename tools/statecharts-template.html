Pi 如何执行一份任务书

主会话先核查前提并整理任务事实。设计组签署方案，实施者提交可复查的版本。两位成员审核同一提交，组长签署后才登记事实并交接。

#1 谁能改变事实和术语

节点说明

  1. 1入口代码读取任务书的目标、事实、交付要求和基线。修复任务先核实报告的现象，新增任务先找出现有能力的缺口。任务书读取代码
  2. 2主会话查证任务前提，指出支持或反驳它的证据。事实管理随后核对每项创建、更新、复用和删除请求。授权不清或与已确认事实冲突时，将判断交还用户。
  3. 3核对通过的变更进入当前工作树的运行检查点。设计者和实施者按任务标签读取相关事实。任务事实视图
  4. 4组长签署当前候选后，插件把任务事实变更与审核决定保留的草稿一起登记，交接阶段取得实际差异。登记代码

#2 谁来处理计划缺口

节点说明

  1. 1三名设计者从相同的任务书、基线和事实快照独立起草。插件等到同一轮草案齐备，再向每人提供另外两份。
  2. 2每位设计者逐项比较、回应和协调。组长综合已经解决的意见，交两名成员确认。与任务书事实冲突的选择交由用户决定。
  3. 3两名成员确认同一版后，组长可签署、要求修订或提交待决问题。签署的方案提交到工作树，实施者据此工作。设计组状态机
  4. 4实施者在方案内决定命名和局部实现，收集与候选提交绑定的验证结果。需要改变设计时，组长接收问题、证据和受影响的步骤。角色分派

#3 哪个版本可以交接

节点说明

  1. 1成员 A 在固定的候选提交上检查行为、目标和草稿事实。明确的问题可以直接交给组长决定返工。
  2. 2初审通过后，插件清理成员 B 的活动审核上下文。成员 B 自己查证，再与成员 A 对照结论与依据。审核状态机
  3. 3组长只能签署已有双方一致通过意见的候选。返工交给原实施者，新候选重新经过初审。受保护事实存在冲突时，由用户裁决。
  4. 4签署后登记事实并准备本地交付记录。对外发送的目标、内容和版本需另获授权。离线方法目录
