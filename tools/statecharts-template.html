#1 谁能改变事实和术语

节点说明

  1. 1① readTaskbook 读取新增／修复入口、目标、交付项和基线。新增项核对现状、目标差异；修复项先找能区分故障和正常行为的复现。参考 PStack · Feature、Bug Fix。
  2. 2② 附加 PStack · Prove It Works。用仓库行号或本轮工具原始回执支持主张；Matt · Domain Modeling 区分名称、定义与适用范围。Magpie 检索结果作为候选；审核者另查基线。
  3. 3③ 独立审核分别判定 P 项观察和 M 项变更。任务书可授权创建、改写或退休某一版事实／术语。未获授权的矛盾交给用户；/taskbook-decide 记录裁决后重新核查。
  4. 4④ applyApprovedMemory 用 Git 版本比较并写入共享台账，保留旧定义、删除理由及审核来源。跨项目准入方法 逐项判定授权与复用范围；通过后发布到 Magpie Memory。远端需改写或撤回时由用户核对；本地定义默认留在项目。

#2 谁来处理计划缺口

节点说明

  1. 1① 参考 PStack · Architect、Feature、Matt · Prototype。设计者先用现有证据收敛问题。方法目录提供适用条件和来源，按任务选择设计、诊断与实验方法。
  2. 2② 设计与执行由主线程切换模型。taskbook_consult 另起无父对话的只读会话，带入明确问题、任务约束和固定提交。taskbook_probe 由子进程在临时检出运行，记录假设、判断条件、命令、退出码及输出。设计者决定观察能否支撑方案。
  3. 3③ acceptPlan 要求每步有标识、行动、验收方式和目标引用，全部目标与交付项均须覆盖。附加 PStack · Sequence Verifiable Units，执行报告绑定计划版本。目标、事实、授权以内的实现细节由执行者决定。
  4. 4④ 执行者提交 plan-gap、步骤、观察与问题。设计者用新计划版本继续；若缺用户授权则经 /taskbook-answer 回到设计。设计与执行共用模型，或同一步骤、观察和问题再次出现，直接交用户。查看 Pi 的分派与恢复代码。

#3 三种独立审核怎样得出交接结论

节点说明

  1. 1① runIndependentReview 每轮新建 SDK 会话。上下文含任务书、适用事实、该角色的检查项和候审证据；通过 inspect_revision 自行读取固定 Git 内容。三个角色均可独立配置模型。
  2. 2② 事实审对每条主张和记忆变更出结论。规格审对目标、交付项、用户对待决问题的原始答复及每条计划判据举证。质量审独立检查候审变动、边界和维护代价。参考并按角色附加 Matt · Code Review 与 PStack · Prove It Works 的方法。
  3. 3③ 代码检查必审项覆盖、观察编号、候审提交和版本。交付缺项退执行者，方案本身有问题走 #2。实验任务由主会话先测量；功能任务可由交付审核要求测量，测后从规格审重过两审。同一候审已测量仍被要求测量，或同一提交和证据反复被退回，均退出并说明阻塞。
  4. 4④ 规格与质量都通过才标为可交接。保留 PStack · Shipping 的独立验证，将自动合并停在用户授权边界。每项方法、原文定位、改写与未采用部分见 完整技能目录（离线网页）。
